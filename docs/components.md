# Component Registry

This is the full component registry of the lm-assist codebase — every shipped component, tracked in one place. lm-assist is **full observability and control for the Claude product line**: Claude Code sessions (local, remote/CCR, and cloud), claude.ai conversations, Cowork, Agent SDK runs, memory and rules, MCP connectors, and usage and limits — cross-node and cross-session. The registry is grouped the way the product is layered: **core-claude** (everything Claude-related), **extended** (capabilities beyond Claude, reached through the ext MCP API — browser connectors, VMs, containers, desktop, GitHub, data service, transfers), and **platform** (the internal plumbing: hub, transport, caches, auth, build and lifecycle). Four doors lead into all of it — the **MCP connector is the main door** (used from claude.ai conversations, Cowork, and Claude Code local/remote), the **Web UI** is watch-and-drive, the **Claude Code plugin** (skills/commands/hooks) is the terminal door, and the **REST API** is for systems.

Reading the tables:

- **Since** — the month of the first commit on the component's path (from git history).
- **Last touched** — the date of the last commit on the path.
- **Freshness** — judged from git history against how fast the rest of the repo moves, honestly rather than as marketing:
  - **active** — commits within roughly the last two months.
  - **stable** — complete and quiet since mid-2026; still exercised.
  - **aging** — untouched since roughly March 2026 or earlier while sibling code moved monthly. It works, but sees no development.
  - **dormant** — no live callers, regardless of commit date.
- **Docs** — links to the docs and runnable examples that cover the component; where none exist yet, the link goes to the source path. Component names always link to the source.

Within each group, flagship components lead: the landscape tier first (session/search tools, mission autopilot and its resilience ticks, CCR, the claude.ai toolkit, Cowork, cross-node memory, the backlog graph, UI panes, the extended connectors, the hub), then major engines and primary surfaces, then supporting pieces, then aging and dormant ones — marked as such.

## How this stays current

This registry is generated, not hand-maintained. The row set comes from a full-codebase component inventory pass; **Since** and **Last touched** come from git history on each component's path (first commit month and last commit date), and the freshness band is judged against how fast the rest of the repo moves — never from what a feature's own description claims. Two rules keep it honest:

- **Aging and dormant components are marked, not advertised.** A component untouched since early 2026 while its siblings moved monthly gets an aging marker; a component with no live callers is dormant regardless of commit dates. Optional, off-by-default features (the knowledge pipeline, memory harvest) are described as opt-in, never as core behavior.
- **Regenerate rather than patch.** When components land, merge, or go quiet, re-run the inventory + registry pass and rewrite this file from the result — spot edits drift. Re-verify every link target against the tree as part of the regeneration (this revision verified all of them).

Current counts: 80 core-claude, 14 extended, 32 platform — 126 components, of which 12 are landscape-tier flagships, 10 are marked aging, and 4 dormant. A small number of rows (the pane gallery and the Claude Code plugin surface) were reconstructed directly from repo ground truth where the inventory input was incomplete; a future regeneration from a complete inventory will backfill anything still missing (for example, docs tooling and packaging scripts beyond the CLI lifecycle).
