# Record-level, project/node-aware Memory Map + Auto-Sync

Status: DESIGN (2026-06-06). Builds on the existing `/memory/*` API (`core/src/api/memory-api.ts`), the chokidar memory cache (`core/src/memory-cache.ts`), the frontmatter parser (`core/src/utils/frontmatter.ts`), shareability classifier (`core/src/utils/memory-shareability.ts`), and the LangMart Hub (`core/src/hub-client/`).

## Goal

A unified, project- AND node-aware memory layer that works at the **record** level (individual memory items inside files), gives a **two-level brief/complete (selectively partial) map** for quick reference/inference across every project and node, treats **CLAUDE.md as a special memory file**, and **auto-detects → registers → syncs** new/changed records from one node to the others (replacing today's manual git pull/push).

## 1. The Record model (the atomic unit)

Today the system is file-level (`MemoryFile`). We add a `MemoryRecord` — the smallest addressable memory item.

```
MemoryRecord {
  recordId   : string   // stable locator: "<node>:<project>:<file>#<anchor>"
  contentHash: string   // sha256 of `complete` — change detection + cross-node dedup
  node       : string   // host/node id (windows-desk, linux-117, ...)
  project    : string   // project slug (-home-ubuntu-lm-unified-trade)
  source     : "live" | "repo:<host>"
  file       : string   // project_broker_boundary.md | CLAUDE.md | MEMORY.md
  kind       : "memory" | "claude-section" | "index-entry"
  anchor     : string   // "" for whole-file memory; heading-path for claude-section; slug for index-entry
  title      : string   // frontmatter.name | section heading | index bullet title
  brief      : string   // frontmatter.description | section summary | index hook   (BRIEF level)
  complete   : string   // full body                                                (COMPLETE level)
  type       : "user"|"feedback"|"project"|"reference"|"claude"|"index"
  shareability: "host-local"|"project-domain"|"ambiguous"
  mtimeMs, size
}
```

### Extraction rules
- **Standard memory file** (frontmatter + body) -> exactly **1 record**. `title=frontmatter.name`, `brief=frontmatter.description`, `complete=body`, `anchor=""`, `kind=memory`. (Matches the "one file = one fact" convention.)
- **CLAUDE.md (special)** -> split on headings into a section tree; each `##` (and significant `###`) -> **1 record**. `anchor` = heading path ("Trade Web > Sanity checks after every restart"), `title` = heading, `brief` = first sentence (or generated 1-liner), `complete` = section body, `kind=claude-section`, `type=claude`. CLAUDE.md is NOT host-synced (it is shared repo-root content, same on every node via git) — it is only *indexed* into the map for reference. One synthetic root record carries the file-level summary.
- **MEMORY.md (index)** -> each bullet -> **1 `index-entry` record** pointing at a memory file's record. Used to detect index/file drift (entry without file, file without entry).

## 2. Two-level reference map (the deliverable)

A generated, cross-project/node index of all records. Two levels, both selectively partial:
- **BRIEF**: `{recordId, node, project, file, title, brief, type}` per record — compact, for fast scan/inference (the "quick memory map").
- **COMPLETE**: full records incl. `complete` bodies.
- **PARTIAL / selective**: filter by `projects[]`, `nodes[]`, `types[]`, `q` (relevance), `since` (mtime) — applied at either level, so any slice (one project, one node, one type, a query) renders at brief or complete depth.

Artifacts (regenerated by the watcher, see §4):
- `~/.lm-assist/memory-map.json` — machine map (all records, both levels in one structure).
- Served live via API (§3) so it is never stale.
- Optional committed human view per node (off by default).

## 3. Unified API (extends `/memory/*`)

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/memory/map?level=brief\|complete&projects=&nodes=&types=&q=&since=&limit=` | The cross-project/node record map, filtered |
| GET | `/memory/records?...` (same filters) | Flat record list |
| GET | `/memory/record/:recordId` | One record (complete) |
| GET | `/memory/map/stats` | Counts per project / node / type / shareability (the overview) |
| GET | `/memory/changes?sinceMs=` | Record-level deltas (added/modified/removed) since a watermark |

MCP tools to add: `memory_map` (brief/complete/partial), `memory_record`. Existing file-level tools stay.

## 4. Auto-detect -> register -> sync (the new requirement)

### Detect (per node)
Extend the chokidar memory-cache so that, on any file event in a watched memory dir, it **re-extracts records** for that file and diffs them (by `contentHash`) against the prior snapshot -> emits record-level events `{added[], modified[], removed[]}`.

### Register (per node)
- Update the in-memory record registry (the map) immediately.
- Append each change to `~/.lm-assist/memory-changes.jsonl` (forensic log + the `since` watermark source for `/memory/changes`).

### Sync to other nodes — two tiers (conflict-free by construction)
Data transport = **git mirror** (safe, auditable, respects per-host-folder ownership); notification = **hub** (low latency):
1. On a change in the **live** auto-memory of a project that has a repo, mirror the file into that repo's `memory/<this-host>/` (the existing push rule, now automated), update the mirrored `MEMORY.md`, `git add/commit/push` — scoped to `memory/<this-host>/` only, so a node only ever writes its own folder (no merge conflicts).
2. After push, emit a lightweight hub event `memory-updated {project, host, recordIds[]}` over the node's existing Hub WebSocket; the hub fans it to other connected nodes; each other node reacts by fetching just the changed mirror (`git fetch` + checkout of `memory/<host>/`) and refreshing its cache -> its map now reflects the new record within seconds.

### Guards
- Debounce (per file, e.g. 1.5 s) + coalesce bursts.
- Only auto-sync `project-domain` / `ambiguous` records; **never** `host-local` (Chrome flags, machine paths, PowerShell quirks) — uses the existing shareability classifier.
- Require valid frontmatter; skip files matching credential patterns; per-node `MEMORY_AUTOSYNC=on/off` flag; observe-only mode first.
- CLAUDE.md changes flow through normal git (it is repo-root, not host-owned); the map re-indexes it on pull.

## 5. Module layout (implementation order)

1. `core/src/memory/record-extract.ts` — file -> `MemoryRecord[]` (memory / claude-section / index-entry). Reuses `parseFrontmatter`; adds a CLAUDE.md heading splitter.
2. `core/src/memory/record-registry.ts` — aggregate records across all projects x sources into the map; filter for brief/complete/partial; stats.
3. `core/src/routes/core/memory-map.routes.ts` — the §3 endpoints; register in `routes/core/index.ts`.
4. Cache hook — record-diff events + `memory-changes.jsonl` in `memory-cache.ts`.
5. `core/src/memory/autosync.ts` — mirror+commit+push on live change; hub `memory-updated` emit; on receive, fetch+refresh. Behind `MEMORY_AUTOSYNC`.
6. MCP tools `memory_map`, `memory_record`.
7. Tests: extractor (incl. CLAUDE.md sections), registry filters, autosync dry-run.

## 6. Why this shape
- Record-level + two-level/partial map = quick inference without loading whole files.
- Git-as-transport keeps the per-host-ownership invariant (no cross-node write conflicts) and an audit trail; hub only carries a notification, so no unsafe remote writes.
- Everything rides infrastructure that already exists (chokidar cache, hub, repo mirrors, frontmatter parser) — this is an extension, not a new system.

## 7. Agent-orchestration tier (Haiku) — LLM orchestrates, scripts produce output

Memory query/search/snapshot is served by a **Haiku** agent spawned through the existing lm-assist agent endpoint (`POST :3100/agent/execute` / `web /api/agent/*`), NOT by deterministic HTTP alone — so a natural-language ask ("what do my machines know about the broker boundary?") maps to the right filtered slice.

**Hard rule — never return LLM-generated memory content.** The agent is an *orchestrator only*: it picks the filters (projects/nodes/types/query, brief vs complete, partial selection) and then **runs the memory CLI** (`node core/scripts/memory-map.js …`, §5/§8) which pulls + combines the **actual** records; the agent returns that script output **verbatim**. The model's own output tokens stay tiny (a filter decision + a pointer), the bytes come from the script. This avoids hallucinated memory and saves tokens on large snapshots.

Flow:
1. Caller -> `/agent/execute` with `model: haiku`, prompt = the memory question + the CLI contract.
2. Agent runs `node core/scripts/memory-map.js --level brief --projects … --q …` (or `--record <id>` for complete).
3. CLI prints the real brief/partial/complete map (JSON or MD) to stdout.
4. Agent returns that stdout as its result (no paraphrase). For huge results the CLI writes a file and the agent returns the path + a head.

## 8. CLI surface (the agent's tool + a human tool)

`node core/scripts/memory-map.js`:
- `--level brief|complete` (default brief)
- `--projects a,b` `--nodes windows-desk,linux-117` `--types project,reference` `--q <query>` `--since <ms>` `--limit N`
- `--record <recordId>` (one complete record) | `--stats` (overview) | `--format json|md`
- Scans every project's live dir + repo mirrors on this node, extracts records (`dist/memory/record-extract.js`), filters, prints. Deterministic; safe to call from the Haiku agent or a shell.

## 9. Provenance + Reconciliation (LLM-managed, script-computed candidates)

### Provenance (per record)
Every `MemoryRecord` carries `originSessionId` (from frontmatter — backtrack the full story in `~/.claude/projects/<proj>/<sid>.jsonl`) and `recordedAtMs` (file mtime = when this state was written). `contentHash` lets us detect when a record actually changed vs a no-op touch. This is the audit spine for everything below.

### Reconciliation (the `reconcile` tier)
A script computes **candidates** deterministically; a Haiku/Sonnet agent (orchestrator, never fabricating content) decides and applies. Three jobs:
1. **Duplicate / merge** — script clusters records by (a) identical `contentHash` across nodes (exact dup), (b) high title/description token overlap, (c) same `anchor`/topic across projects. LLM reviews each cluster, proposes a canonical record + which to retire, and (for cross-host dups) which host folder owns it. Output = merge plan; apply only on confirm.
2. **Dependency edges** — script extracts `[[wikilink]]` references already used in memory bodies + filename/title co-mentions to build a draft dependency graph; LLM confirms/labels edges (supersedes, depends-on, relates-to). Stored alongside the map.
3. **Outdated detection** — script flags records whose `recordedAtMs` is old AND whose subject was contradicted by a newer record (same anchor, higher mtime, conflicting `contentHash`), or whose referenced files/commands no longer exist (cross-check against the repo). LLM confirms "outdated/superseded by X" — never auto-deletes; marks for review.

All three run through the agent tier (§7): the script emits the candidate set as data; the LLM returns a decision plan; a separate apply step (git-mediated, per-host-ownership) executes confirmed changes. Nothing is auto-deleted without a recorded decision + the originSessionId trail.

## 10. The two-stream architecture (canonical framing)

Everything above composes into **two continuous streams + a harvester**, all sharing the §1 record model and §3 unified API.

### Stream A — Background maintenance (write side, continuous)
Runs per node as part of lm-assist Core. Pipeline on every memory change:
`watch (chokidar) -> detect record-level delta (by contentHash) -> register (map + memory-changes.jsonl) -> categorize -> sync across nodes (git-mirror + hub-notify, §4) -> auto-manage / reconsolidate (§9: dedup/merge, dependency mapping, outdated)`.
Detection/registration/sync are deterministic + immediate; reconsolidation is periodic and agent-mediated (LLM decides, script applies, per-host-ownership + originSessionId trail).

### Stream B — Front query (read side, on demand)
`front "get memory by search" (NL + context) -> backend agent (Haiku, §7 orchestrator) -> runs the map CLI to pull RELATED records (query + category + dependency edges) -> decides brief vs complete PER record (a mix) -> returns the actual assembled slice (verbatim script output, never fabricated)`.
The result is partial + related + mixed-depth: high-relevance records complete, supporting ones brief.

### Harvester — session -> candidate memory (feeds Stream A)
A separate LLM agent periodically scans recent session files (`~/.claude/projects/<proj>/<sid>.jsonl`, by recent mtime) for content worth persisting as memory that is not yet captured (diffed against the existing map). It proposes new records **classified into a category**, sets `originSessionId` for provenance, and routes them to Stream A for write (human/agent confirm before commit). Avoids duplicates by checking the map first.

### Category taxonomy (orthogonal to `type`)
`type` = provenance class (user/feedback/project/reference/claude/index). `category` = semantic role, the axis the harvester classifies into and both streams filter on:
`architecture · deployment · component · endpoint · feature · config · lesson (knowledge/lessons-learned) · knowledge (catch-all) · index`.
Extensible. A rule-based categorizer assigns a default at extraction; the reconcile/harvest agent refines and can re-tag. Category is a first-class filter in `/memory/map` and the CLI (`--category`).

## 12. The Harvester is a deep analyst, and the system is a timestamped self-validating registry

The harvester (Opus) is NOT a recorder. Its job is to keep memory the **authoritative, current, timestamped view of the project** — every record knows when it was written AND when it was last confirmed true. Temporal fields on every record: `recordedAtMs` (written), `lastValidatedMs` (last confirmed still-true), `validity` (current|stale|outdated|superseded), optional `validFrom`/`validUntil`, and `supersededBy`.

### What the harvester reasons about (per candidate + per existing record)
1. **Why memory at all** — is this significant, non-obvious, and NOT already captured by the code itself, CLAUDE.md, or a design doc? Trivia and things derivable from the repo are rejected.
2. **Validity window** — from when is it true, and until when / under what condition does it stop being true? Validity is tied to **code/feature state** (e.g. "valid while the broker boundary lives at scripts/broker/", "valid until the 3001->3011 port move ships to npm").
3. **Outdated / superseded detection** — re-validate existing records against the **current** code, features, endpoints, and docs. If a record names a file/function/flag/endpoint that changed or no longer exists, or a newer record contradicts it, mark `outdated`/`superseded` (never auto-delete) and set `supersededBy`. Automates the CLAUDE.md rule "if a memory names a file/function/flag, verify it still exists."
4. **Document-awareness** — scan the project docs (CLAUDE.md sections, `docs/`, README, design plans), understand **each document''s purpose and its own validity-till**, and reconcile memory against them: do not duplicate what a doc authoritatively owns; flag divergence (memory says X, doc says Y) for the reconcile tier.

### Triggers
- On a session''s end / recent-change scan (the harvest pass).
- On code/feature change signals (git commits touching files referenced by records) -> re-validate the affected records'' `validity` + bump `lastValidatedMs`.
- Periodic full re-validation sweep.

### Result
The map answers not just "what do we know" but "what is **currently true**, since when, last checked when, and what superseded what" — across every project and node. Stream B can prefer `validity=current` and surface "last validated N days ago" so stale knowledge is visibly stale.

## 13. Graded confirmation — how the harvester knows a fact is TRUE

A memory record is only as trustworthy as its evidence. Every record carries a `validationTier` and the harvester earns it from ranked evidence sources (highest wins, recorded with `lastValidatedMs` + the source):

| Tier | Evidence | How the harvester confirms |
|---|---|---|
| `code-confirmed` | The codebase itself | Harvester reads the actual code/config and verifies the fact holds (file/function/endpoint/flag exists and matches). Independent, strongest. |
| `session-confirmed` | The originating Claude Code session | Harvester reads the session transcript and sees the work was **developed -> tested -> validated** (tool results show tests passing, a round-trip succeeded, the user confirmed). Strong when the session shows verification, weaker when it only shows intent. |
| `asserted` | Stated in a session/doc but not verified | Claimed but no test/code evidence yet — provisional. |
| `unvalidated` | Default at extraction | Nobody has checked. Extractor sets this; harvester upgrades it. |

The harvester escalates: start from the session''s work-status (cheapest — already have the transcript), and **drop into the codebase to validate directly only if needed** (the session is ambiguous, or the record is high-stakes, or time has passed since `lastValidatedMs`). On a code/feature change touching a record''s referenced files, the record''s tier is reset toward `unvalidated` until re-confirmed — so the registry never silently claims a stale fact is `code-confirmed`.

This composes with §12: `validity` (current/outdated/superseded) = is it still true *now*; `validationTier` = how do we *know*. A Stream B answer can show both ("code-confirmed, current, last checked 2d ago" vs "asserted, validity unknown").
